# 投稿と集計のためにサーバーを持ち、ログインは持たない

[ADR-0002](./0002-フレームワークとサーバーを持たない.md) では、サーバー・データベース・ログインをいずれも持たないと決めた。利用者ごとの状態はブラウザの中に置けば足り、サーバーを持たないことが「個人情報を管理しなくてよい」という利点にもなっていた。

この決定のうち、**サーバーとデータベースについては覆す**。ログインを持たないことは維持する。

## 何を作るか

利用者どうしがつながる機能として、次の二つを作る。

- **絶景スポットの投稿** — 利用者が撮った写真と場所を投稿できる。
- **累積人気** — 成因カードが開かれた回数を絶景スポットごとに数える。

一方、当初あわせて検討していた二つは作らない。

**行動履歴による個性化は、サーバーを必要としない。** よく開かれたテーマを学習して成因カードの並び順に反映するのは、行動履歴も判断も一人の端末の中で完結する。ログインを持たない以上、端末をまたいで引き継ぐこともできない。サーバーを挟む理由がないので、これは前端だけで作る（[将来構想 2](../将来構想.md)）。詳細は下の「行動履歴の扱い」に書く。

**遅延情報のリレーは見送る。** [将来構想 8](../将来構想.md) が挙げていた「同時に乗っている利用者がいないと動かない」という問題に加えて、より重い問題がある。どの列車にいるか、何分遅れているかは、どちらも端末が自己申告する値で、サーバーには検証する手立てがない。匿名で、利用者数も少ない状態では、複数の報告を突き合わせて確からしさを上げることもできない。誤った遅延が一件表示されるだけで、ホームにいる人が乗るのをやめてしまう。**この作品で唯一、間違いが利用者に実害を与えうる機能だった**ため、作らないことにした。

## 行動履歴の扱い

**何を数えるか。** 成因カードを開いた回数と、開いていた時間の両方を持つ。開いてすぐ閉じたものと、最後まで読んだものを区別したいためで、5〜6 コマある読みものでは、この差が興味の差をよく表す。

**どちらも端末から出さない。** 累積人気としてサーバーへ送るのは**開いた回数だけ**にする。滞在時間は送らない。「この絶景は 120 回開かれた」は誰にでも意味が読み取れるが、「平均 43 秒」は読み取れる意味がない。公開する数値としての用をなさないものを、わざわざ人の行動として持ち出す理由がない。滞在時間を端末の中に閉じておけば、送信の失敗を考えなくてよいという利点もついてくる。

**時間の測り方には、この作品に固有の落とし穴が三つある。**

- 画面が隠れたら時計を止める（`visibilitychange`）。別のアプリへ移った、画面を消した、電話が来た——カードは開いたままでも読んではいない。
- **車上モードは Screen Wake Lock で画面を消さないようにしている**（設計書 4.3）。したがって「画面がついている」は「読んでいる」の証拠にならない。ふつうのウェブページより滞在時間を過大に見積もりやすい。
- 一度に数える上限を 120 秒に切る。カードを開いたまま鞄に入れれば、一回の乗車で数百秒が積み上がり、順位が壊れる。

**結果をどこに出すか。** テーマの絞り込みスイッチを自動で操作することはしない。利用者が決めた見え方を横取りしないという設計書 4.1 の原則に反するためである。反映するのは次の二つに限る。

- 成因カードを読み返すときの並び順。
- テーマチップの**印の大きさ**。よく読むテーマは大きく、あまり読まないテーマは小さく出す。

大きさを使うのは、不透明度と彩度がすでに埋まっているためである。不透明度はテーマの on / off と天気の良し悪しに、彩度は天気に割り当たっている。ここへ三つ目の意味を載せると、利用者は「自分が消したのか」「天気が悪いのか」「よく読んでいないのか」を区別できなくなる。

ただし大きさを変えてよいのは**印だけ**で、ボタンそのものの寸法（46×40）は変えない。設計書 4.1 は、画面が変わってもボタンの置き場所を動かさないことを繰り返し求めている。チップの箱ごと伸び縮みさせると、隣のチップが左右にずれる。押す位置が回ごとに変わるのは、揺れる車内ではいちばん避けたい。

段階は 24 / 28 / 32px の**三段だけ**にする。連続に変えると、大きさの違いが意図ではなく不具合に見える。既定は 28px で、読んだ記録が 3 件たまるまではすべて 28px のままにする。データが乏しいうちから決めつけない。

## なぜ Supabase か

制作者 2 名はいずれもサーバー側の開発経験がない。Supabase は PostgreSQL に REST API とオブジェクトストレージと HTTPS が最初から付いてくるので、**サーバーのコードを書かずに済む**。書かないコードには不具合も出ない。学ぶ対象が SQL とアクセス制御の設定だけに絞られる。

前端は GitHub Pages のままでよい。静的ファイルの配信先を変える必要はなく、`fetch` の宛先が増えるだけである。

## どこまでを持つか

サーバーを持つと決めた以上、何を持たないかを決めておかないと際限がなくなる。

**ログインは持たない。** 投稿は匿名で受ける。メールアドレスもパスワードも預からない。端末をまたいだ引き継ぎは、できないものとして設計する。

**投稿は、審査を通るまで公開しない。** 投稿されたものは公開されない領域に入り、制作者が目で見て通したものだけが表に出る。公開してから問題を見つけて下げる方式も検討したが、匿名で、投稿数に上限がなく、確認が一日一度である以上、その組み合わせでは安全にならない。作業量はどちらも「一日一度見る」で変わらないので、公開を後にするほうを採る。

**投稿には保存期限を設ける。** 2027 年 4 月 30 日にすべて削除する。現地展示（2027 年 3 月 17〜19 日）の終了から約 6 週間後にあたる。他人の写真を預かる以上、いつ手放すかを先に決めて投稿画面に書いておかないと、投稿する人は自分の写真がどうなるか分からないまま押すことになる。制作者が学業を終えたあとも、預かったままの個人情報だけが残り続けるのも避けたい。

**投稿者の IP アドレスは、ハッシュにしてから 90 日だけ持つ。** 何も持たないと投稿数に制限をかけられず、削除の求めにも応じられない。そのまま持つと、それ自体が預かる個人情報になる。ハッシュであれば、同じ相手からの投稿かどうかは分かり、その値から相手をたどることはできない。

**テーマ色は投稿には与えない。** 4 つのテーマ色は地理的な意味を表す色である（設計書 5.4）。成因カードを持たない投稿にこの色を割り当てると、そこに意味があるように見せてしまう。投稿のバッジは無彩色にする。

## 後端が無くても作品は動く

**`data/` 以下は一つもサーバーへ移さない。** 絶景スポット、時刻表、路線、地形はこれまでどおり静的ファイルとして配信し、乗車前にブラウザへ保存する。サーバーが持つのは、投稿と回数という「増えていくもの」だけにする。

サーバーへの問い合わせは 3 秒で打ち切り、失敗しても画面にエラーを出さず、その機能を**出さない**。投稿レイヤーが現れない、回数が表示されない、それだけになる。通知も地図も成因カードも旅の記録も、これまでと同じように動く。

この形にしておく理由は三つある。銚子電鉄の沿線には電波の弱い区間があり、設計書 9.3 の「通信が切れても通知は動く」という性質を手放したくないこと。Supabase の無料枠は一定期間使われないと停止するため、審査員が URL を開くときに動いている保証がないこと。そして、万一のときに一行で静的な作品へ戻せるようにしておきたいこと。

## Consequences

- 設計書 7.1 の「ただし送信先がない。サーバーもデータベースも持たない構成なので、写真は端末の外へ出しようがない」は成立しなくなる。書き換えが要る。ただし**車上モードで撮った写真は引き続き端末の外へ出ない**。外へ出るのは、利用者が投稿を押したときだけである。この境界を文章にも実装にも残す。`js/journal.js` の冒頭にも同じ趣旨のコメントがあるので、あわせて直す。
- 設計書 9.1 の技術構成図と 9.2 の「採用しないもの」の表を更新する。ログインを採用しないことは残る。
- この作品は他人の個人情報（顔が写りうる写真と、その撮影場所）を預かることになる。安全管理措置の義務は、預かっているあいだ続く。2027 年 4 月 30 日の削除をもって終える。
- 投稿画面には、本人が撮影したものであること、人物が判別できる写真は投稿しないこと、16 歳未満は保護者の同意を得ること、保存期限を書く。写真は端末側で EXIF を落としてから送る。どの絶景スポットの近くで撮ったかは `journal.js` が既に記録しているので、EXIF を落としても失われる情報はない。
- **アクセス制御の設定ミスが単一障害点になる。** Supabase の匿名キーは前端の JavaScript に現れるので、安全は Row Level Security だけが担保する。書き込みはすべて関数経由にし、`service_role` の鍵は前端に置かない。公開前に、匿名キーだけで「未審査の投稿が読めないか」「行を消せないか」を実際に試す。
- 投稿も回数も、利用者が増えるほど意味を持つ機能である。公開直後と現地展示の時点では、どちらもほぼ空になる。投稿レイヤーを既定で隠すのはこのためでもある（[mockup-decision](../../ai/artifacts/利用者投稿/mockup-decision-地図バッジ.md)）。

## 追記：この決定の前提が一つ、実測で崩れた（2026-08-11）

累積人気を Supabase に載せ、匿名キーだけで実際に叩いてみたところ、**回数はいくらでも増やせた**。`S01` の回数を、HTTP ヘッダを付け替えるだけで 1 から 4 まで押し上げられた。

誰が開いたかは IP アドレスで見分けている。端末が名乗る ID を信じないのは、名乗り直せば何度でも数を増やせるからで、そこまでは正しかった。崩れたのはその先の「IP なら端末から偽れない」という前提のほうである。IP は `x-forwarded-for` というヘッダから読んでいたが、このヘッダは**端末が自分で書いて送れる**。代理は上書きせず、本物を末尾に足すだけだった。したがって値は「詐称値, 本物」と連なる。丸ごと訪問者の鍵にしていたので、詐称部分を変えるたびに別人になれた。

実測でわかったヘッダの素性は次のとおり。

| ヘッダ | 素の値 | 詐称したとき |
|---|---|---|
| `x-forwarded-for` | 本物 | 「詐称値, 本物」と連なる |
| `cf-connecting-ip` | 本物 | **変わらない**（送ろうとすると Cloudflare が門前払いする） |
| `x-real-ip` | 無い | — |

そこで `cf-connecting-ip` を先に見て、無ければ `x-forwarded-for` の**末尾だけ**を採るようにした（`supabase/schema/001_spot_opens.sql` の `visitor_key()`）。修正後、同じ手口で 5 回試しても回数は 1 のまま動かない。連鎖を 3 段に伸ばして末尾採りを迂回しようとしても同じだった。

**この一件は、上の「アクセス制御の設定ミスが単一障害点になる」という項目の範囲を広げる。** そこで想定していたのは権限の設定ミス——読めてはいけない行が読める、消せてはいけない行が消せる——であり、それらは公開前の検査で 8 項目すべて通っていた。今回の穴は権限ではなく、**入力をどこまで信じるか**の取り違えだった。権限が完璧でも、関数が信じてよい値と信じてはいけない値を取り違えていれば、正規の入口から堂々と壊される。

数字が刷られてもデータは壊れず、誰の個人情報も漏れない。それでも見送らなかったのは、累積人気が**画面に出る数字**であり、テーマチップの印の大きさにも反映されるためである。現地展示で「この絶景は 1 万回開かれました」と出ているものが、実際には誰かの手癖だったという状態は、作品の信用に直に関わる。

検査は `supabase/local/setup_and_verify.sql` に足した（9〜11 番）。手元の PostgreSQL には HTTP 要求が無いが、`request.headers` はただの設定値なので、手で置けば解釈の部分は確かめられる。11 番は対照で、「どの IP でも同じ鍵を返す」という壊れ方で 9・10 番を素通りさせないために置いてある。

以後、**サーバー側で信じてよいのは、端末が書けない値だけ**とする。投稿機能でも同じ問いが出る（投稿者の名乗り、撮影時刻、位置）。いずれも端末の自己申告なので、それらを根拠に何かを制限する作りにはしない。
